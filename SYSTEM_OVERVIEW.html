01   Project Objective

travelbuddy was built to demonstrate a production-grade multi-agent AI system applied to a real-world domain — travel planning. The project objective is to move beyond the common pattern of a single LLM handling all tasks, and instead architect a system where specialised AI agents collaborate, each owning a distinct area of responsibility, coordinated by a supervisor and grounded in live retrieved data.

PRIMARY OBJECTIVE

Build a working multi-agent travel assistant that provides accurate, current and cited travel information — covering trip planning, safety advisories, weather, activities and emergency contacts — through a clean web interface backed by a production-ready API.

TECHNICAL OBJECTIVE

Demonstrate LangGraph supervisor pattern, RCG prompting, parallel agent execution, live web search tool integration, session memory, and CI/CD-ready containerised deployment as a reference architecture for production multi-agent systems.

PROBLEM BEING SOLVED

Travel planning requires information from multiple specialist domains simultaneously — safety advisories, visa rules, weather, logistics and local knowledge. A single generalist LLM produces generic, unverifiable answers. Domain-specific agents with live data retrieval produce specific, sourced, trustworthy answers.

KEY DESIGN PRINCIPLE

RCG (Retrieval-Contextual Grounding) — agents are reasoners over retrieved data, not knowledge stores. Every claim must be traceable to a live tool result. This is especially critical for advisory information where outdated data can have real consequences for travellers.

03   Solution Description

travelbuddy is a real multi-agent AI travel assistant built on LangGraph's supervisor pattern. Unlike a single LLM pretending to handle multiple roles, travelbuddy runs six genuinely independent LLM instances in parallel — each with its own identity, tools, system prompt and area of responsibility. Every agent retrieves live data from the internet before reasoning, so responses are always current and source-cited rather than recalled from training memory.

The system is built on RCG (Retrieval-Contextual Grounding) prompting — agents are reasoners over retrieved context, not knowledge stores. A structured context packet is injected into every agent before tool calls, parallel agent outputs are wrapped in XML tags for clean synthesis, and model strength is matched to task complexity (gpt-4o for safety reasoning and synthesis, gpt-4o-mini for routing and retrieval tasks).

The backend is a FastAPI server that compiles and runs the LangGraph graph, maintains session memory per conversation, and serves the web UI. Everything runs in Docker with a single docker compose up command.

06   RCG Prompting Implementation

RCG (Retrieval-Contextual Grounding) is implemented across four files, each fulfilling one of the four goals.

Leverage — Comprehensive Context
app/graph/nodes.py → _build_context_packet()
Every agent receives a structured brief before calling tools: destination, dates, duration, origin, purpose, and an explicit grounding reminder. Agents are not just given the raw user message — they are given everything extracted from the entire conversation.
Structure Extensive Inputs
app/graph/synthesiser.py → _build_xml_section()
Five parallel agent outputs are wrapped in <agent_output> XML tags before reaching the synthesiser. Each section contains <retrieved_data>, <agent_reasoning>, and <structured_outputs> — the model navigates them by name, not by position.
Task–Model Alignment
app/config.py + app/agents/specialists.py
Three model tiers: gpt-4o-mini for routing (clarifier, supervisor), gpt-4o-mini for retrieval agents, gpt-4o for advisory (safety-critical) and synthesiser (complex multi-source merge). AdvisoryAgent overrides the base class constructor.
Comprehensive Context — Specialist Topics
app/agents/specialists.py → system prompts
Every system prompt explicitly instructs: "You are a REASONER over retrieved data — never answer from training memory." The advisory agent must call all four tools and cite source name + date for every claim. If a tool returns no data, it says so rather than guessing.
